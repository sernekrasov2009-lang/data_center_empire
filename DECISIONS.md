# Решения (DECISIONS)

Короткие записи о выборе, который не описан в GAME.md/DESIGN.md напрямую.

## Этап 0

1. **Стек без лишних библиотек.** Только `react`, `react-dom`, `zustand` в рантайме. Роутер, i18n-библиотека, UI-кит и `uPlot` не подключались: экран один, тексты в двух JSON, графиков пока нет. Любая новая библиотека — только после согласования (GAME.md, разд. 2).

2. **Electron собирается через `tsc`, а не через плагин Vite.** `npm run build:electron` кладёт `electron/main.ts` и `preload.ts` в `dist-electron/`. Плагины `vite-plugin-electron`/`electron-vite` не добавлялись, чтобы не тянуть лишние зависимости.

3. **Dev-режим запускает `tools/dev.mjs`.** Скрипт сам поднимает Vite (через API), дожидается адреса, собирает main-процесс и запускает Electron с `VITE_DEV_SERVER_URL`. Без `concurrently`/`wait-on`. Vite слушает `127.0.0.1` (в v8 по умолчанию он занимает только IPv6, и окно получало `ERR_CONNECTION_REFUSED`), адрес берётся из `resolvedUrls` и проверяется запросом перед запуском окна. Для отладки через CDP: `UPTIME_DEBUG_PORT=9222 npm run dev`.

4. **Контракт моста — `src/platform/api.ts`.** Preload импортирует тип оттуда, поэтому `tsconfig.electron.json` использует `rootDir: "."`, а `main` в `package.json` указывает на `dist-electron/electron/main.js`. Так интерфейс и preload не расходятся.

5. **Симуляция остаётся чистой.** `src/sim/` не знает про React, DOM и Electron; аккумулятор реального времени и `requestAnimationFrame` живут в `src/state/`. Функция `advanceTicks` не мутирует входное состояние — Zustand получает новый объект.

6. **Новая игра стартует на паузе.** Игрок сначала осматривается, время включает сам. Скорость по умолчанию ×1.

7. **Темп времени — данные, не код.** `hoursPerRealSecond`, длины суток/месяца, скорости, лимиты кадра и размер журнала событий лежат в `src/data/balance.json` и проверяются тестом. Сутки на ×1 = 60 с, на ×60 = 1 с (DESIGN.md, разд. 1).

8. **CSP только в собранной версии.** В dev Vite и react-refresh вставляют inline-скрипты, которые строгий CSP заблокировал бы. Плагин `productionCsp` добавляет мета-политику при `vite build`.

9. **Язык интерфейса пока в `localStorage`.** Настройки и их файл появятся на этапе 1; до этого выбор языка хранится в `uptime.language`, по умолчанию — русский. *Этап 1:* язык переехал в `settings.json` (`game.language`), ключ в `localStorage` больше не используется.

10. **Шрифты — системные.** Внешние шрифты не подключались: используется системный стек (Segoe UI / Noto / DejaVu) и моноширинный для чисел. Вопрос лицензий (OFL) отпадает; собственный шрифт можно добавить позже.

11. **События пока возвращаются из `advanceTicks`, а не идут через шину.** Шина (`serverFailed`, `customerJoined`, …) появится на этапе 2, когда возникнут первые системы-подписчики; сейчас это была бы мёртвая абстракция.

12. **Пустая заглушка вместо нарисованных KPI.** На дашборде KPI показываются как «—» с подписью «появится на следующих этапах», чтобы не показывать выдуманные числа.

## Этап 1

13. **Версия состояния игры — 2, версия файла настроек — 1.** `companyName` и `difficulty` добавлены в `GameState`; старые сохранения поднимаются в `src/save/migrate.ts` (неизвестные значения заменяются безопасными, битые файлы отклоняются с `SaveError`). `settings.json` версионирован отдельно, потому что настройки живут вне сейва и общие для всех игр.

14. **Формат сохранения — gzip + отдельный `.meta.json`.** Меню и список слотов читают метаданные, не распаковывая сейв целиком. Запись атомарная (временный файл → rename), перед записью ротируются три бэкапа `.bak1..3`; при повреждении основного файла слот читается из бэкапа и игрок получает предупреждение.

15. **Сложность влияет только на данные старта и множители.** `startMoney`, `failureRateMult`, `eventRateMult`, `slaPenaltyMult`, `bankruptcy` лежат в `src/data/difficulties.json`; код сложностей не знает и берёт параметры из файла. Санбокс отключает отказы и события нулевыми множителями, а не отдельной веткой логики.

16. **Режим «без рамки» применяется при следующем запуске.** Electron не умеет менять `frame` у живого окна. В текущей сессии выбор временно работает как полноэкранный режим, а настоящее окно без рамки создаётся при следующем старте; подсказка в интерфейсе это объясняет.

17. **VSync не переключается игрой.** Значение сохраняется в `settings.json` и показывается в интерфейсе, но фактическое переключение выполняет драйвер или ОС — Electron не даёт принудительно управлять вертикальной синхронизацией. В подсказке это написано прямо.

18. **Звуковые ползунки пока только сохраняются.** Звуковой движок (WebAudio) по плану — этап 15. Настройки громкости, гула, тревог и приглушения при потере фокуса уже есть в файле и интерфейсе, чтобы не менять формат `settings.json` позже.

19. **Лимит FPS прореживает шаг симуляции, а не кадры.** `requestAnimationFrame` продолжает идти, но `advance` вызывается не чаще заданного лимита; накопленное время не теряется. Так лимит влияет на нагрузку, не ломая расчёт времени.

20. **Масштаб интерфейса — `zoom` на `#root` с обратными размерами.** Отдельного layout-движка нет: `--ui-scale` задаёт `zoom`, `--ui-inverse` компенсирует размеры, `--font-size` меняет базовый кегль. Это единственный способ увеличить весь интерфейс без переписывания вёрстки на `rem`.

21. **Браузерный запасной мост.** `src/platform/index.ts` реализует настройки и слоты через `localStorage`, если `window.uptime` нет. Это позволяет проверять меню и диалоги в обычном `vite` и в тестах; в Electron всегда используется реальный IPC.

22. **Запасной seed — `crypto.getRandomValues`.** «Случайный» seed в диалоге новой игры берётся из `crypto`, а не из `Math.random`: правило детерминизма распространяется на всю игру, а не только на `src/sim/`.

## Этап 2

23. **Все числа экономики — в `src/data/economy.json`.** Тарифы на электричество, PUE по локациям, тарифы интернета, стартовая нагрузка, аренда, порог банкротства и размер истории отчётов лежат в данных и проверяются `validateEconomy`. Код берёт значения через `getElectricityTariff`, `getInternetPlan` и `economy`.

24. **Версия состояния игры — 3.** Добавлены `economy` (начисления, отчёты, итоги за всё время, множитель цены, флаг предупреждения) и `gameOver`; миграция v2 → v3 заполняет их безопасными значениями. Отчёты обрезаются до `reports.historySize`, отрицательные суммы и множитель вне границ обрезаются при чтении.

25. **Начисление и счёт разделены.** Электричество копится каждый тик в `economy.accrual`; в конце месяца списываются накопленное электричество, интернет и аренда, после чего пишется `MonthlyReport`. Выручка пока равна нулю — доходы появятся вместе с клиентами на этапе 5.

26. **Дрейф цены электричества — раз в год через seeded RNG.** Случайный шаг ±`priceDriftPerYear` (5%) ограничен множителями 0,8–1,2. 31 декабря сначала выставляется счёт за декабрь, затем закрывается год и меняется тариф: иначе декабрьский счёт зависел бы от будущей цены.

27. **Банкротство определяется сложностью.** `gameover` останавливает время и показывает незакрываемый экран, `warnings` (спокойная) только предупреждает и позволяет играть дальше, `none` (песочница) молчит. В режиме `gameover` автосохранение после рокового счёта не выполняется, чтобы не затирать живые сейвы мёртвым состоянием.

28. **Дашборд собирается из отдельных панелей.** `EconomyPanels.tsx` содержит баннер долга, счёт текущего месяца, расшифровку, прогноз на три месяца и последние шесть счетов; история хранит 24 отчёта. Формат денег показывает центы для сумм меньше $1000, чтобы счёт за электричество не округлялся до целых долларов.

## Этап 3

29. **Каталог железа целиком в `src/data/components.json`.** Названия моделей, цены, потребление, шум, MTBF, сокеты, форм-факторы, параметры магазина, доставки и ремонта лежат в данных и проверяются `validateHardware`. Названия комплектующих пока выводятся из данных как есть: это вымышленные бренды, переводить их не нужно. Интерфейсные подписи вокруг них идут через i18n.

30. **Стартовый домашний ПК — обычная готовая сборка.** Он описан теми же семью деталями каталога и сразу имеет статус `ready`, поэтому попадает в расчёт нагрузки и может ломаться, как любой другой сервер. Суммарно это ровно 100 Вт — прежняя стартовая нагрузка из `economy.json`; при отсутствии готовых сборок движок всё равно откатывается к этим 100 Вт.

31. **Потребление электричества считается по фактическим сборкам.** `hardwareLoadW` суммирует потребление всех готовых серверов; новая сборка увеличивает счёт со следующего часа, а не после перезапуска. Прогноз счёта использует ту же нагрузку.

32. **Экономика этапа 3 упрощена.** Цена новых деталей умножается на один общий месячный множитель 0,9–1,1 (независимо для каждой детали не хранится); б/у рынок — шесть лотов, обновление раз в неделю, скидка 30–60%, MTBF ×0,5, скрытый дефект с шансом 10% в первые 60 дней. Доставка: новые 1–3 дня, б/у 1–5 дней, бесплатно от $200, иначе $10. Отмена — первые 12 часов, возврат — 3 дня с комиссией 10%.

33. **Ремонт автоматический.** Отказы проверяются раз в сутки; при отказе деталь чинится 48 часов, но если на складе есть такая же деталь, она расходуется и ремонт занимает 6 часов. Выбора «чинить или менять» пока нет — это решение придёт вместе с обслуживанием на следующих этапах.

34. **Размещение, оптовые скидки и дефицит отложены.** Стойки и размещение относятся к этапу 4, оптовые скидки и корпоративный поставщик — к эпохе 3, дефицит деталей — к этапу событий. В магазине стоит пояснение, чтобы упрощение не выглядело багом.

35. **Версия состояния игры — 4.** Добавлен блок `hardware`; миграция v3 → v4 создаёт стартовую сборку, пустые склад и заказы и сразу наполняет б/у рынок. При чтении отбрасываются детали и заказы с неизвестными `componentId`, счётчики id поднимаются выше максимальных, множитель цены ограничивается 0,5–1,5.

## Этап 4

36. **Числа локации целиком в src/data/location.json.** Климат (сезонная кривая по месяцам, суточная амплитуда ±5 °C с пиком в 15:00, минимум комнатной температуры 12 °C — дом отапливается), пороги 35/45/55 °C, шум (ночь 22:00–08:00 с лимитом 30 дБ, день 50 дБ, раздражение 0,2/дБ·ч, спад 0,15/ч, жалоба при 12%, штраф  при 24%, отключение при 48%), шумоизоляция (, −8 дБ) и варианты охлаждения проверяются validateLocation. Все пороги берутся из данных, интерфейс их только показывает.

37. **Проводимость окна и вентилятора поменяны местами относительно DESIGN.md §4.3.** В дизайне бесплатное окно имело C = 40 Вт/К, а платный вентилятор  — C = 25 Вт/К, то есть платное охлаждение было хуже бесплатного. В данных окно — C = 25 Вт/К, вентилятор — C = 40 Вт/К, и покупка имеет смысл: холоднее, но шумит (+12 дБ).

38. **Автомат выбивает после часа перегруза, а не через 60 секунд.** Тик симуляции — один игровой час, поэтому отсчёт 60-секундного окна в рамках тика дробить нечем: перегруз держится один час без последствий, выбивает на втором часе (breakerGraceHours = 1 в location.json). Сброс автомата бесплатный, но перегруз вернётся, пока нагрузка не упадёт ниже ёмкости.

39. **Слот — единственный источник размещения.** Поле HardwareBuild.slot (null — собран, но не размещён) заменяет отдельный массив слотов в состоянии: один сервер занимает один слот, перемещение выталкивает прежнего жильца. Готовые сборки автоматически занимают свободные слоты (в тике железа и при миграции), ручное размещение — выбор в экране локации. Снятый со слота сервер не потребляет электричество и не шумит.

40. **Электричество считается по состоянию локации.** ИТ-нагрузка — сумма работающих (размещённых и не выключенных) сборок × PUE + потребление охлаждения; при выбитом автомате вся цепь обесточена и охлаждение тоже. Интернет и аренда берутся из state.location и определения локации, а не из economy.start, поэтому смена тарифа сразу видна в прогнозе счёта. Отказы железа зависят от комнатной температуры и не проверяются при выключенных серверах.

41. **Версия состояния игры — 5.** Добавлен блок location и поле slot у сборок; миграция v4 → v5 создаёт локацию с безопасными значениями (неизвестное охлаждение и тариф заменяются дефолтами, раздражение и температуры обрезаются по диапазонам), расставляет готовые серверы по слотам — стартовый первым, дубликаты слотов снимаются.

## Этап 5

42. **Числа услуг целиком в src/data/services.json.** Три стартовые услуги из DESIGN.md §5.1 (сайт-визитка, CMS, чат-боты) с ресурсами на клиента и ценой, параметры спроса (эластичность 1,5, репутация 0,7, цена 50–200% от рынка), оттока (3%/мес базово, +2%/мес за цену выше 120% рынка) проверяются validateServices. Репутация — константа из данных, станет динамической на этапе 7.

43. **Клиенты хранят цену подписки.** ClientState фиксирует pricePerMonth на момент подписки: смена слайдера цены действует только на новых клиентов, старые продолжают платить по своей цене. Это упрощает UI (не надо пересчитывать выручку ретроактивно) и даёт игроку естественную механику «поднять цену для новых».

44. **Выручка начисляется почасово, а списывается в конце месяца.** Каждый час clients × pricePerMonth / 720 копится в services.monthRevenue; в billMonth накопленное переносится в MonthlyReport.revenue и добавляется к деньгам вместе со счётом. Простой (выбитый автомат, перегрев, соседи) останавливает начисление, но не теряет клиентов — SLA-штрафы за простой появятся на этапе 7.

45. **Best-fit размещение по серверам.** Новый клиент идёт на сервер с наименьшим нормированным остатком ресурсов (ядра + ОЗУ/8 + диск/500), где он помещается. Полоса интернета считается общей по локации: сумма mbitPerClient всех клиентов не может превышать тариф. Переразмещения при снятии сервера со слота пока нет — это оверселлинг/миграции будущих этапов.

46. **Спрос по Пуассону через seeded RNG, отток — вероятность в сутки.** Приток: samplePoisson(Knuth) по λ из формулы DESIGN §5.2, ограничен лимитом услуги и свободными ресурсами. Отток: базовый 3%/мес пересчитан в суточную вероятность, сверх цены >120% рынка — ещё 2%/мес. Часть дня с выключенной услугой просто не даёт λ.

47. **Версия состояния игры — 6.** Добавлен блок services; миграция v5 → v6 создаёт блок с рыночной ценой и выключенными услугами. При чтении цена обрезается в 50–200%, лимит — в 0…100000, клиенты с неизвестной услугой или несуществующим buildId отбрасываются, nextClientId поднимается выше максимального. События clientsJoined/clientsLeft добавлены в допустимые.

## Этап 6

48. **Бот-стратегия живёт в `src/sim/bot.ts`, а не в tools.** Это чистая логика над игровым состоянием (без React/DOM), тестируемая Vitest наравне с остальной симуляцией; CLI — только тонкая обёртка. Рецепты серверов (budget/mid/big) захардкожены в боте: это стратегии проверки баланса, а не игровые данные.

49. **Симулятор грузит движок через Vite SSR, а не дублирует его.** `tools/balance-sim.mjs` вызывает `server.ssrLoadModule("src/sim/index.ts")` — прогоны идут ровно тем же кодом, что и живая игра, при этом не нужно собирать Electron-бандл или выносить симуляцию в отдельный npm-пакет.

50. **Веха $1000/мес недостижима дома — это фича, а не баг.** Прогон seed 1337, 720 дней: 2 слота home → 2 сервера → 98 клиентов → потолок ~$568/мес. Таблица темпа §10.1 для доступной части выполняется ($50–150/мес в начале — в норме); дальнейший рост требует гаража (этап 9), что и есть задуманный мотив переезда. Симулятор честно показывает причину застоя («нет свободных слотов (локация «home»: 2)»), а не молчит.

## Этап 7

51. **Аптайм считается по клиенту, а не по серверу.** Час засчитывается как простой компании, если хоть один клиент сидит на неработающем сервере (выбитый автомат, перегрев или сломанная деталь). Это простое агрегирование по услугам в отчёте месяца; поточечная статистика по каждому клиенту избыточна для текущей механики.

52. **EMA репутации обновляется раз в сутки, а не раз в час.** Формула DESIGN §6 — скользящее среднее за ~60 дней; шаг 1/60 в сутки даёт то же окно при меньшем числе пересчётов. Накопители простоя/качества копятся почасово, поэтому точность не теряется.

53. **Ежедневные события репутации вытесняют старые из кольцевого журнала.** `reputationChanged` пишется только при изменении значения (после выхода на плато событий нет), но при плавном росте появляется каждый день. Тесты движка переведены с `state.events` (буфер 60) на `result.events` (полный список за вызов) — это правильный источник для проверки порядка событий.

54. **SLA-штраф — месячная доля оттока, применяется до следующего отчёта.** При закрытии месяца `closeMonthReputation` возвращает штраф по услугам (пункты × 0,01/мес), движок кладёт его в `services.slaPenalty`, а тик оттока добавляет штраф к базовой вероятности ухода. Клиенты не уходят мгновенно при аварии — волна уходит в течение следующего месяца, что читается как «недовольные разбежались после отчёта».

55. **Версия состояния игры — 7.** Блок reputation: значение, счётчики месяца (просто/качество/часы), открытые тикеты с id, аптайм прошлого месяца, рейтинг последнего отзыва. Повреждённый блок заменяется стартовым состоянием (0,7), тикеты санируются, накопители месяца не переносятся (счёт пересчитается).

## Этап 8

56. **Мировые события живут в блоке `world`, а не в `events`.** `GameState.events` — кольцевой журнал `SimEvent` с давней историей; новое состояние («какие аварии активны прямо сейчас») — отдельный блок `world` с `active[]` и множителем цены электричества. Роллится раз в сутки на границе дня, тикается каждый час.

57. **Блэкаут и сбой канала — причины `powerOff`, а не отдельные флаги.** Механика простоя этапа 7 уже считает недоступность по `powerOff !== "none"`: выручка не начисляется, часы простоя копятся, SLA штрафует. Переиспользование причин означает, что аварии автоматически интегрированы во все существующие проверки (activeBuilds, operationalBuildIds, размещение клиентов).

58. **Парирование аварий — будущие этапы, вероятности применяются как есть.** ИБП и генератор появятся с гаражом (этап 9), защита от DDoS и «Безопасность» — с исследованиями (этап 11), RAID/бэкапы — там же. Структура `ActiveEventState` рассчитана на будущие проверки смягчений: достаточно добавить условие в `rollDailyEvents`.

59. **Мировые события не переносятся при миграции v7 → v8.** Блок `world` создаётся пустым: продолжать блэкаут после загрузки сейва бессмысленно (часы события могли потерять смысл), а множитель цены электричества слишком мелкий, чтобы тащить через миграцию.

60. **Переезд — только на следующую локацию (home → garage).** `moveLocation` проверяет порядок `home → garage → colo → datacenter` и отклоняет прыжки через ступеньку кодом `locationNotAdjacent`. Прыжки вперёд сломали бы баланс (colo требует другого масштаба денег), а возврат назад не нужен по дизайну.

61. **Переезд сбрасывает изоляцию, охлаждение и раздражение соседей.** Шумоизоляция — свойство старого помещения, охлаждение/тариф — дефолты новой локации. Серверы снимаются со слотов и расставляются автоматически по завершении 24-часового простоя (`powerOff = "moving"` — та же механика простоя, что и блэкаут).

62. **ИБП гасит блэкауты ≤ 4 ч целиком, без частичных случаев.** `maxMinutes/60` сравнивается с длительностью ролла: блэкаут 2 ч пропускается без простоя (событие `blackoutPrevented`), блэкаут 5+ ч работает как без ИБП. Промежуточная механика «ИБП держит 4 ч, потом падает» добавила бы дробные простои без игровой ценности на текущем этапе.

63. **Гараж остаётся шумной локацией (соседи по кооперативу).** Механика шума/штрафов действует и в гараже; изоляция покупается заново. В balance-sim без изоляции бот платил штраф $50 каждые 2–3 дня (~$10 500 за 720 дней) — поэтому бот покупает изоляцию сразу после переезда.

64. **GameState остаётся v8 в этапе 9.** Новые поля локации (`upsOwned`, `stabilizerOwned`, `movingUntilHour`) — примитивы с безопасными дефолтами (false/null) в `asLocation`; отдельная версия не нужна.

65. **Персонал — по одному сотруднику на роль.** Штат из 6 ролей без дублей упрощает UI и баланс: эффект роли суммируется только через уровни (сила × уровень), а не через количество. Уволить и нанять заново можно в любой момент.

66. **Эффекты персонала — проценты до 90%, а не выключатели.** Каждая роль даёт `strengthPerLevel × уровень` (5–15% за уровень): сисадмин ускоряет ремонт, электрик/сетевик сокращают длительность аварий, безопасник режет шанс взлома, поддержка ослабляет штраф тикетов, продажник усиливает приток. Потолок 90% гарантирует, что механики не отключаются полностью.

67. **Зарплаты списываются в счёте за месяц, а не ежедневно.** `staff` — четвёртая строка `ExpenseBreakdown` рядом с интернетом и арендой: один момент списка, видно в прогнозе, банкротство по тем же правилам.

68. **Уровень растёт каждые 90 дней работы, максимум 5.** Зарплата ×1,2 за уровень: к 5 уровню +107%, уровень становится долгосрочной инвестицией. Промоушен — суточный тик `tickStaff`, событие в ленту.

69. **Бот нанимает персонал только при выручке ≥ $1200/сотрудник.** Зарплаты ($1500–3500) — вес эпохи 2–3 с выручкой $3–10 тыс.; в 720-дневном прогоне бот зарабатывает $600–1300 и осознанно не нанимает — механика проверяется ручной игрой и тестами, а не баланс-симом.

70. **Плотность размещения — деление требований клиента, а не умножение сервера.** Виртуализация/оркестрация делят cores/ram/storage на (1 + бонус) в `fits`: одна и та же сборка принимает больше клиентов, а предельные метрики сервера не искажаются. Проще для UI и миграций: в state нет ничего нового.

71. **Услуги открываются добавлением в `services.services` при завершении исследования.** Стартовый набор фиксируется `STARTER_SERVICE_IDS`; state с мигрированными сейвами не «узнаёт» об услугах, которых не должно быть, а разблокировка — единственная точка входа.

72. **Максимум 2 исследования параллельно, отмена возвращает 50%.** Параллельность ограничивает «запустить всё сразу», возврат половины делает отмену осмысленной, но не бесплатной.

73. **Бот исследует только после вехи $1000/мес.** Ранний старт виртуализации ($800) задерживал веху с 510 на 660 день: исследования — апгрейд работающей экономики, а не замена заказов серверов.

74. **Зарплата сотрудника бота ≤ 60% месячной выручки.** Ошибка этапа 10 проявилась при выручке $1270: наём поддержки ($1500/мес) гарантированно топил счёт. Теперь найм требует запаса, а не только взноса.

## Этап 12

75. **Антикризис бота (порог строго отрицательный).** Честные тарифы по локации (гараж $0,09 вместо домашнего $0,12) сместили траекторию бота: 12-й сервер в гараже перегревался на вентиляторе, а правила не давали выйти из петли shutdown → рестарт → отток. Фикс комплексный:
    - тепловой лимит `tryOrderServer`: при fan/window бот не заказывает серверы, выходящие за ~750 Вт тепла, и копит на сплит ($650);
    - рестарт серверов блокируется при `fan` и температуре ≥ 35 °C — сначала апгрейд охлаждения;
    - резерв перед заказом сервера = полный месячный счёт (`projectedMonthlyExpenses`), а не $200: в colo фиксированных $200 не хватает;
    - накопление на исследования: пока не хватает денег на проект, серверы не заказываются;
    - антикризис при `money < 0`: уволить самого опытного сотрудника, снять со слота серверы без клиентов, вернуть лишнюю стойку арендодателю. Все пороги отрицательные: положительный порог срезал нормальный рост.
    Итог (seed 1337): веха $1000/мес — день 450, colo достигается ~день 955, пик выручки $3641, банкротства нет в 1800-дневном прогоне.

76. **Шум соседей не действует в colo.** В арендованном зале шумит весь colo, отдельных соседей нет: жалобы и штрафы после переезда — баг. `tickLocation` считает раздражение только для `home`/`garage`.

77. **Стойки в colo можно вернуть арендодателю.** Аренда $500/мес за пустую стойку — неснижаемый расход, из-за которого бот дважды банкротился при оттоке клиентов по SLA. `returnRack` запрещает возвращать последнюю стойку и стойку с серверами в слотах; бот возвращает лишние в антикризисе.

78. **Тариф электричества зависит от локации.** Раньше все локации считались по домашнему тарифу $0,12/кВт·ч. Теперь home — бытовой $0,12, garage — коммерческий $0,09, colo/datacenter — промышленный $0,06. Это честнее и быстрее выводит на colo, но сдвинуло эталонные вехи: $1000/мес теперь день 450 (было 510).
